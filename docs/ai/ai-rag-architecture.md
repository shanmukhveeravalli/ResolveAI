# ResolveAI — AI Foundation & Retrieval-Augmented Generation (RAG) Architecture

## 1. Overview & Core Philosophy

In mission-critical enterprise incident management, operational stability and data integrity are paramount. ResolveAI integrates artificial intelligence not as an autonomous, unchecked actor, but as an **evidence-grounded advisory copilot** designed to assist on-call engineers and service desk managers.

### 1.1 Fundamental Architectural Principles

1. **Human-in-the-Loop (Zero Auto-Mutation)**:
   - The AI analysis endpoints (`/api/ai/incidents/{id}/analyze` and `/api/ai/incidents/{id}/rag-analyze`) are strictly read-only (`@Transactional(readOnly = true)`).
   - AI outputs **never** alter incident category, priority, severity, status, or assignee in the database directly.
   - Suggestions are advisory recommendations presented through the UI. Human engineers or managers review, approve, or adjust recommendations before ticket mutation.

2. **Strict Failure Isolation (Zero Cascading Outage)**:
   - The platform treats AI providers as external auxiliary dependencies.
   - If an AI provider is unconfigured, disabled (`resolveai.ai.enabled=false`), times out, or fails with an HTTP error, the system throws `AiServiceUnavailableException`.
   - The `GlobalExceptionHandler` converts this to an RFC 7807 compliant `503 SERVICE_UNAVAILABLE` payload.
   - Core operational capabilities—incident reporting, status transitions, SLA calculations, notifications, and analytics—remain 100% operational regardless of AI status.

3. **Vendor-Independent Abstraction**:
   - The domain service interacts solely with high-level Java interfaces (`AiProvider` and `EmbeddingProvider`).
   - The active provider is dynamically selectable via configuration (`resolveai.ai.provider`).

4. **Data Minimization & Privacy**:
   - Prompt sanitization filters out sensitive customer data, passwords, hashes, and internal secrets.
   - Prompts contain only operational ticket information (title, description, and current categorization).

## 2. Implemented Subsystems: Phase 10 vs. Phase 11

ResolveAI implements two distinct AI subsystems:

| Feature Dimension | Phase 10: AI Advisory Foundation | Phase 11: Grounded RAG Pipeline |
| :--- | :--- | :--- |
| **Primary Endpoint** | `POST /api/ai/incidents/{id}/analyze` | `POST /api/ai/incidents/{id}/rag-analyze` |
| **Purpose** | Immediate incident triage, summarization, and severity suggestion. | Deep diagnostic assistance grounded in institutional knowledge and resolved historical tickets. |
| **Data Source** | Current incident title and description only. | Current incident context + Top-K Knowledge Articles + Top-K Historical Incidents. |
| **Retrieval Engine** | None (direct prompt completion). | `pgvector` HNSW cosine similarity search over 1536-dimensional embeddings. |
| **Output Schema** | `suggestedCategory`, `suggestedPriority`, `suggestedSeverity`, `summary`, `analysis`. | `diagnosis`, `resolutionSuggestion`, `confidence`, and cited `sources` (`RagSourceDto`). |
| **Evidence Citations** | None. | Explicit citations with source ID, title, similarity score, reference label, and snippet. |
| **Rate Limit** | 20 requests / 60 seconds | 20 requests / 60 seconds |

## 3. Component Details & Pipeline Stages

### 3.1 AI Provider Abstraction (`com.resolveai.ai.provider`)

- **`AiProvider` Interface**:
  ```java
  public interface AiProvider {
      IncidentAnalysisResponse analyzeIncident(IncidentAnalysisPrompt prompt);
      RagAnalysisResponse generateGroundedAnalysis(RagAnalysisPrompt prompt);
  }
  ```
- **`EmbeddingProvider` Interface**:
  ```java
  public interface EmbeddingProvider {
      List<Double> generateEmbedding(String text);
  }
  ```
- **`OpenAiCompatibleAiProvider`**:
  - Implemented using Spring Boot 3 `RestClient`.
  - Connects to OpenAI-compatible endpoints (`/chat/completions`).
  - Configurable timeouts (`connectTimeout`, `readTimeout`).
  - Validates and parses JSON structured outputs with fallback handling.
- **`OpenAiCompatibleEmbeddingProvider`**:
  - Emits HTTP POST requests to `/embeddings`.
  - Generates 1536-dimensional dense float vectors using models such as `text-embedding-3-small`.

---

### 3.2 Dense Vector Storage & Search (`pgvector`)

Vector embeddings are persisted in dedicated PostgreSQL tables:

```sql
-- Knowledge Article Embeddings
CREATE TABLE article_embeddings (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    article_id BIGINT NOT NULL UNIQUE REFERENCES knowledge_articles(id) ON DELETE CASCADE,
    embedding vector(1536) NOT NULL,
    model VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_article_embeddings_hnsw ON article_embeddings USING hnsw (embedding vector_cosine_ops);

-- Historical Incident Embeddings
CREATE TABLE incident_embeddings (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    incident_id BIGINT NOT NULL UNIQUE REFERENCES incidents(id) ON DELETE CASCADE,
    embedding vector(1536) NOT NULL,
    model VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_incident_embeddings_hnsw ON incident_embeddings USING hnsw (embedding vector_cosine_ops);
```

#### Vector Search Implementation (`VectorSearchService.java`)
- **Production Engine (PostgreSQL)**:
  - Executes SQL cosine distance queries (`ORDER BY embedding <=> CAST(? AS vector) LIMIT ?`).
  - Converts distance to similarity (`similarity = 1.0 - distance`).
  - Enforces visibility filters:
    - **Knowledge Articles**: Only articles with `status = 'PUBLISHED'` are queried for RAG.
    - **Historical Incidents**: Only incidents with `status IN ('RESOLVED', 'CLOSED')` are queried. Excludes the current incident ID.
- **Test Compatibility Engine (H2)**:
  - Automatically detects H2 in-memory databases during tests.
  - Falls back to in-memory cosine similarity calculation over serialized float arrays, ensuring full test isolation without requiring external database extensions in CI.

### 3.3 Text Preparation & Prompt Construction (`RagTextPreparationService.java`)

1. **Query Text Normalization**:
   - Concatenates incident title and description with structural delimiters.
   - Cleans control characters and truncates within token thresholds.
2. **Context Assembly**:
   - Injects top-ranked Knowledge Articles with problem, root cause, and resolution extracts.
   - Injects top-ranked Historical Incidents with recorded resolution notes.
3. **Structured System Prompt**:
   - Instructs LLM to generate evidence-grounded hypotheses only.
   - Explicitly instructs LLM to produce citations corresponding directly to provided context items.
   - Computes an estimated `confidence` score (0.0 to 1.0) based on source relevance.

### 3.4 Citation Data Model (`RagSourceDto.java`)

Every returned RAG recommendation includes structured citation metadata:

| Field | Type | Description |
| :--- | :--- | :--- |
| `sourceType` | `RagSourceType` | `KNOWLEDGE_ARTICLE` or `HISTORICAL_INCIDENT` |
| `sourceId` | `Long` | Primary key of the source entity |
| `title` | `String` | Title of the article or incident number/title |
| `similarity` | `Double` | Cosine similarity score (0.0 to 1.0) |
| `reference` | `String` | Human-readable label (e.g. `KB-14` or `INC-20260901-089`) |
| `snippet` | `String` | Extracted relevant text excerpt used in the prompt |

## 5. Security & Rate Limiting

- **Access Control**: Both `/analyze` and `/rag-analyze` endpoints are restricted to `ENGINEER`, `MANAGER`, and `ADMIN` roles.
- **Resource Ownership**: `AuthorizationService.canAccessIncident()` verifies that the caller has legitimate visibility over the incident (e.g., assigned engineer, team manager, or admin).
- **Rate Limiting**: Enforced at 20 requests per 60 seconds per user (`@RateLimit(limit = 20, periodSeconds = 60)`).
- **Credentials Protection**: API keys are injected via environment variables at runtime and never logged or exposed in error messages.
